# Wazuh の TLS、チェックポイントの発行、検証履歴の技術検収

## Scope

Wazuh 接続確認スクリプト、チェックポイントを発行する CLI、検証結果を記録する CLI、履歴を読むモニターと API を対象にする。[Task 20261127-06](../tasks/TASK.verification-evidence-11-27-2026.md)

## Acceptance Criteria

| 操作・条件 | 期待する結果 |
| --- | --- |
| 認可済みローカルサービスの合成証明書を信頼する CA とホスト名で接続する | 認証とアラート取得に同じ TLS 検証を適用する。CA を信頼できない、またはホスト名が一致しない接続では資格情報を送らない。 |
| 正しい案件と、別案件の ID を使って同じ実行のチェックポイントを発行する | 正しい案件で発行できる。台帳と異なる案件は `cross_campaign_ref` で拒否し、誤った案件にチェックポイントを作らない。 |
| CLI から台帳とチェックポイントをそれぞれ検証する | 履歴に検証方法を記録し、その時点で確かめた末尾やチェックポイントの識別情報を表示できる。旧記録にない値は未記録と判断できる。 |
| 大きな履歴、履歴ファイルなし、空ファイル、読めない行を含む履歴を開く | 正常な行を取得できる場合はページを移動して読める。取得できない場合や一部の行を省いた場合は画面・API で区別できる。 |
| operator と Blue から同一の検証を確認する | operator は検証対象の詳細を確認でき、Blue は従来の公開項目だけを受け取る。 |

## Evidence

手順は[製品操作ガイド](../PRODUCT-GUIDE.md)、検証コマンドとページ単位の取得方法は [CLI・HTTP 契約](../requirements/API-CONTRACTS.md)で確認できる。関連する試験は [Wazuh 接続確認](../../tests/test_wazuh_smoke.py)、[合成証明書での TLS 確認](../../tests/test_wazuh_smoke_tls.py)、[ブラウザーからの履歴操作](../../tests/browser/verification-history.browser.mjs)。

## Verification Result

製品コミット `398214ff015dd7d296de2e8292540a90c5c052a5` の技術検収は合格した。正式 manual-bb の strict プロファイルで P0 の5件と P1 の3件がすべて通り、判定は `go` だった。必須の観測項目はすべて確認した。

- Wazuh の模擬サーバーでは、正しい CA とホスト名で認証と取得の2リクエストを受けた。CA が未信頼、ホスト名が不一致、指定した CA ファイルがない、の3条件では終了コード1となり、サーバーが受けた HTTP リクエストは各0件だった。
- 別案件へのチェックポイント発行は `cross_campaign_ref` で拒否され、ワークスペースと信頼済みルートのファイルは操作前後で一致した。正しい案件では1件を発行し、再発行でも同じ値を返した。2種類の検証 CLI が記録した末尾の連番・ハッシュは元の台帳と、チェックポイントのダイジェストは別途再計算した値と一致した。
- 履歴が1,048,576バイトのときは従来形式で全件を取得でき、1バイト超えると 409 と `verification_paging_required` が返った。新しい順に25件ずつ2ページを取得し、50件に重複はなかった。幅1440 pxと375 pxの Chromium で履歴を移動し、ファイルの欠落・空ファイル・旧形式を区別できた。Blue の API と画面では検証対象のハッシュを公開しなかった。
- 正式ゲートの回帰20件がすべて成功し、変更行332行のうち295行を通過した（88.855%）。ローカルの全体回帰は Python が846件成功・8件スキップ、JavaScript が35件成功。独立した静的レビューは4領域を確認し、重大度 blocker・critical の未解決指摘は0件だった。

実運用の Wazuh、実際の資格情報、顧客の台帳は今回の検収対象外。最終 PR head に対する正式 manual-bb と CI の結果は [PR #24](https://github.com/RNA4219/ai-yori-murasaki/pull/24) に記録する。
