# 10万案件の一覧と台帳の検証

## Scope

[10万案件のモニター一覧](../tasks/TASK.monitor-index-11-23-2026.md)を対象とする。確認時刻は台帳・検知を照合した時点を示す。登録、個別案件の全証跡、履歴の全体図は従来の経路を使う。

## Acceptance Criteria

- Rust製の検証器で従来のJSON制約と証跡のハッシュ列を確認し、欠損・改変を集計済みの0件に含めない。
- 10万個の案件IDを50件ずつ取得できる。先頭・中間・末尾へ移動しても、ページの閲覧は台帳を読み直さない。
- 新しい索引は構築完了時に切り替える。構築失敗後も直前の確認時刻とデータで一覧を読める。

## Evidence

Windows・Python 3.11で [検証・索引の回帰試験](../../tests/test_monitor_index.py)と既存のモニター・判断画面のPython試験を実行し、60件が成功した。Windowsでシンボリックリンクを作成できないため1件をスキップした。日時、型、長さ、重複検知、台帳改変、読み取れない実行、Blueへの投影、失敗した再構築を含む。[ブラウザー回帰試験](../../decision_view/browser/dual-view.browser.mjs)は1440・768・390pxのChromeで実行した。

従来と同じ4案件・台帳4本・合計1,000イベントで、案件一覧のAPI処理を交互に各7回計測した。中央値はPython検証が536.32 ms、Rust検証が101.07 msで、全応答のバイト列が一致した。両条件とも索引を使用していない。

負荷試験には異なる10万案件・10万台帳を用意した。各台帳に1件の正当なイベントを置き、検知は0件とした。既存形式のカタログは21,100,035バイト。初回構築は別プロセスのCLIで実行し、ページの測定はネットワークを除いたAPI処理で行う。[評価条件](../evaluation-manifests/EV-20261123-04.json)

## Verification Result

索引の初回構築は714.42秒。Windows上で10万個の別々の台帳を読み、Rust製のスキーマ検証とハッシュ列の確認を行い、SQLiteへ書いた。同じ10万ファイルを使った過去の構築時間は未計測。ウォームアップ後に各ページを11回ずつ計測した中央値は、1ページ目1.281 ms、1,000ページ目4.216 ms、2,000ページ目6.309 msだった。全2,000ページで全IDが入力どおりに1回ずつ現れ、すべての検知件数が集計済み0件だった。[計測結果](../evidence/monitor-index-20261123/results.json)

同じ索引を実サーバー・Chromeの1440pxと390pxで開き、案件数・確認時刻の表示、ページ指定、前後・末尾への移動、モニターと判断画面の各50行を確認した。モニターの閲覧時に全件の承認取得や個別台帳への追加リクエストは発生しなかった。評価条件と結果の事前・事後検査、ロックファイル検査とwheel構築も通過した。

[再現用の見本生成器](../../tests/fixtures/monitor_scale_store.py)は新しいディレクトリに案件を作る。パッケージをインストールした環境で次の順に実行できる。

```powershell
python tests/fixtures/monitor_scale_store.py <新しい絶対パス>
aym --workspace <絶対パス>/workspace --trusted-root <絶対パス>/trusted monitor index
aym --workspace <絶対パス>/workspace --trusted-root <絶対パス>/trusted monitor serve
```

この計測の対象は既存台帳の索引作成と閲覧である。案件を新規登録する側のカタログ書き込みには、従来の単一JSONのサイズ上限がある。
