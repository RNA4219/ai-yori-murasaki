# 10万案件のモニター索引を差分更新する

## Scope

[索引の差分更新](../tasks/TASK.incremental-monitor-11-23-2026.md)を対象とする。入力は異なる10万案件に台帳を1本ずつ持つ合成ストア。1案件に検知を追加し、モニター一覧の表示順・全項目・検知抜粋を対象に照合する。[評価条件](../evaluation-manifests/EV-20261123-06.json)

## Acceptance Criteria

- 通常のCLIによる差分更新では、変更のない99,999本の台帳本文を開かない。
- 同じストアを `--full` で検証し直した結果と、10万行すべての内容・並び順が一致する。
- 一覧更新後、確認時刻を公開する直前に失敗しても、旧一覧と確認時刻を保持する。同じ入力で再試行できる。

## Evidence

[再現用の検証プログラム](../../tests/fixtures/verify_monitor_incremental.py)は専用の一時ディレクトリでCLIを呼び出す。Pythonの監査フックで `events.jsonl` を開いた実行IDと回数を記録する。ファイル属性の取得とSQLite索引の読み取りは台帳本文を開いた回数に含めない。失敗試験では確認時刻を書き込むSQLiteの操作を中断させる。

```console
python tests/fixtures/verify_monitor_incremental.py --count 100000
```

Windowsの[回帰試験](../../tests/test_monitor_index.py)では、サイズと更新日時を保った変更、実行の移籍・追加・削除、カタログだけの所属変更、複数の実行で共有する検知の欠損・復旧、manifestだけの変更を確認した。既存索引の移行、I/O障害、遅い段階での書き込み失敗、トランザクション内から別接続で旧一覧を読めることも検査した。

## Verification Result

WSL2・ext4・Python 3.12.3で、初回は100,000本の台帳を開いた。中央の案件に検知を追加すると、差分更新で本文を開いたのは `r050000` の1本だけだった。同じ入力を全件再構築すると100,000本を開き、表示順の10万行が差分更新結果と完全一致した。[実測結果](../evidence/monitor-incremental-20261123/results.json)

同じ案件の名前を変更し、公開直前に書き込みを失敗させた。一覧は10万行すべて一致し、operator・Blueのページも更新前と一致した。確認時刻は失敗前後とも `2026-11-23T05:49:22.447740+00:00`。失敗要因を除いて再試行すると、同じ台帳1本を開いて新しい名前と確認時刻が反映された。

Windows・Python 3.11でモニター・サーバー・判断画面のPython試験は65件成功、シンボリックリンク作成権限に依存する既存試験が1件スキップ。構成図のJavaScript試験は6件成功した。
