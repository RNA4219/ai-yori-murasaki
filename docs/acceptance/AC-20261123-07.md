# 10万案件の案件詳細と前回比較

## Scope

対象はモニターの案件詳細と、そこから移動する同じ案件の判断画面。系列が3回続いた案件を10万案件の中央に置き、一覧の先頭ページにない案件を直接開く。[Task](../tasks/TASK.indexed-case-detail-11-23-2026.md)・[評価条件](../evaluation-manifests/EV-20261123-07.json)

## Acceptance Criteria

- 詳細では対象案件、判断では対象と比較に必要な直前の案件だけの台帳を開く。
- 今回の検知、前回から新しく入った項目、前回からなくなった項目が画面に現れる。
- 両画面の案件別APIは、同じ台帳を従来の方法で集計した応答と一致する。

## Evidence

独立した10万案件にそれぞれ1本の台帳ファイルを作り、索引を構築した後にブラウザーを起動した。Pythonの監査フックで、各画面を開いた際にサーバーが開いた `events.jsonl` の実行ID・回数と旧カタログの読み取りを数えた。詳細から判断画面へのリンクをクリックし、追加・消失の欄を展開して各項目を確認した。

同系列3件の同じ台帳・manifest・検知を別ストアに複製し、索引を持たない従来のAPIで期待値を求めた。詳細、実行一覧、評価、RSI、判断の5応答は、状態コードと全項目を照合した。呼び出すたびに変わる判断結果の生成時刻だけを照合から除いた。10万件のストアでは評価未登録の応答を確認し、評価レポートがある場合は[別の回帰試験](../../tests/test_v2_assessment.py)で照合した。

再現環境はWSL2、ext4、Python 3.12.3、Python用Playwright 1.65.2とChromium。プロジェクトの依存を導入し、Chromiumをインストールしてリポジトリ直下で実行する。[検証プログラム](../../tests/fixtures/verify_monitor_detail.py)

```sh
PYTHONPATH=. python tests/fixtures/verify_monitor_detail.py --count 100000
```
