# 10万件からの案件受付と再送

## Scope

[案件受付と登録索引](../tasks/TASK.case-intake-11-23-2026.md)を対象とする。規模の単位は独立した受付記録。登録が初期監査や既存の実行カタログに依存しないことを確認する。

## Acceptance Criteria

- 受付済みの案件が10万件ある状態で、公開CLIから新規の1件を追加できる。
- 同じ要求を再送すると、最初に発行した受付IDと受付日時が返る。同じキーで案件名を変えたときは競合として扱う。
- 同時に届いた同じ要求を1件にまとめる。登録結果をモニターから検索できる。

## Evidence

Windows・Python 3.11で、[受付の回帰試験](../../tests/test_case_intake.py)9件が成功した。最初の1件を製品コードで登録し、同じSQLiteスキーマへ99,999件の合成データを一括投入した。異なる受付IDが100,000件あることを照合し、それ以降の操作は毎回独立したCLIプロセスから実行した。

| 操作 | 台帳件数 | 確認結果 |
| --- | ---: | --- |
| 初期データを用意 | 100,000 | 受付IDはすべて異なる |
| 新しい案件を登録 | 100,001 | 受付IDと受付日時を取得 |
| 同じキー・同じ案件名を再送 | 100,001 | 初回の応答と一致 |
| 同じキー・違う案件名を送信 | 100,001 | `idempotency_conflict`、終了コード2 |

別の試験では、空のワークスペースに4プロセスから同じ要求を同時に送信した。全プロセスが成功し、全応答の受付記録が一致し、台帳は1件だった。書き込みを途中で失敗させた試験では、失敗前の件数を保ち、原因を取り除いた後に同じキーで登録できた。

## Verification Result

10万件での登録、再送、検索までを終えたワークスペースには `case-intake.sqlite3` だけが存在し、監査実行は作成されなかった。Chromeの1440px・390pxでモニターから受付台帳を開き、案件名と受付IDの検索、該当なし、Blueビューでの非公開を確認した。

既存のモニター索引・サーバー・画面に関する試験は47件成功、Windowsのシンボリックリンク作成権限によるスキップが1件。ソース配布物からWindows向けwheelをビルドし、新しい仮想環境にインストールした `aym` でも10万件からの追加と再送を確認した。これは受付の機能検収で、登録速度や処理量は測定していない。

