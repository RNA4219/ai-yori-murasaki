# 判断の画面とモニターの両立の仕様 SPEC-DUAL-VIEW（R-064〜R-070）

作成: Claude (Fable 5.2) / 2026-11-16 / 入力: [要件拡張 R-064〜R-070](REQUIREMENTS-DUAL-VIEW.md)、main 746321e の `ai_yori_murasaki/server.py`・`ai_yori_murasaki/assessment.py`・`ai_yori_murasaki/web/index.html`・`decision_view/`・`pyproject.toml`、[API-CONTRACTS](API-CONTRACTS.md)、[SPEC-ASSESSMENT](SPEC-ASSESSMENT.md)、[FRONTEND-DESIGN](FRONTEND-DESIGN.md)、[MONITOR-ASSESSMENT](MONITOR-ASSESSMENT.md)。

本稿は、要件拡張 R-064〜R-070 の画面と配信を定める。2026-11-22に案件の選び方と課題の読み方を更新した。配信には既存のモニター機能、API の応答、`schemas/v1/` のスキーマを使う。

本稿は、R-050 の手順（GLM の設計とレビュー）を通していない（要件拡張の D-065）。代わりに、起草者が問いを立て、リポジトリの記録とユーザーの決定で答えを固めた。別の目として、モデル（Qwen3.8）にも読ませ、指摘を確かめて反映した。問いと答えは 11 節に残す。

## 0. 範囲

- 入るもの: 判断の画面を配る経路、判断用の JSON を返す API、2 つの画面の切り替え、判断の画面で Campaign を選ぶ画面、判断の決まり（評価の状態の使い方、進捗率を出さないこと）。
- 入らないもの: モニターの既存の機能の変更、記録への書き込み、新しい記録の種類、評価と RSI の計算、是正案の中身と承認の操作、公開の操作。
- 採らない案: 判断の画面の中に、全件の表、Run の一覧、課題ごとの出来事を作る案（2026-11-16 に試作した）。モニターの作り直しになり、R-066 に反する。

## 1. 画面と経路（R-064）

| 経路 | 開くもの | いま |
|---|---|---|
| `/` | モニター（Campaign の一覧） | ある |
| `/#/campaign/<campaign_id>` | モニターの Campaign 詳細 | ある |
| `/#/run/<run_id>` | モニターの Run 詳細 | ある |
| `/decision` | 判断の画面の、Campaign を選ぶ画面 | 足す |
| `/decision?campaign=<campaign_id>` | 判断の画面（その Campaign） | 足す |

- `/decision` は、判断の画面の HTML を返す。安全のためのヘッダーは `/` と同じにする（`_security_headers()`。インラインのスクリプトとスタイルはハッシュで許可する）。
- HTML の上限は、`/` と同じ 256 KiB とする。いまの `decision.html` は約 41 KiB である。
- `/decision` は GET と HEAD だけを受ける。Host と Origin の検証は、ほかの経路と同じにする。
- 起動は `aym monitor serve` だけとする。判断の画面のためのコマンドやポートは足さない。

## 2. 切り替え（R-065）

### 2.1 置き場所と言葉

- どちらの画面も、ページの先頭に、「判断の画面」と「モニター」の 2 つを並べる。
- いまいる側は、いまいる場所として示す（`aria-current="page"`）。相手側はリンク（`a[href]`）にする。同じタブで開き、ブラウザーの「戻る」で戻れる。
- 切り替えの部品は、操作できる大きさを 44px 以上とし、フォーカスが見えるようにする。

### 2.2 行き先

| いまの場所 | 切り替えで開く場所 |
|---|---|
| モニターの一覧（`/#/`） | `/decision` |
| モニターの Campaign 詳細（どのタブでも） | `/decision?campaign=<同じ campaign_id>` |
| モニターの Run 詳細 | `/decision?campaign=<その Run の campaign_id>` |
| モニターの資料（`/#/sources` とその下） | `/decision` |
| 判断の画面の、Campaign を選ぶ画面（`/decision`） | `/#/` |
| 判断の画面（`/decision?campaign=<campaign_id>`） | `/#/campaign/<同じ campaign_id>` |

- Run の `campaign_id` をまだ読めていないときは、`/decision` を開く。
- 判断の画面で課題を開いたときにも、「モニターでこの Campaign を見る」を出す。行き先は `/#/campaign/<campaign_id>` である。
- 課題ごとの位置（評価タブの中のその検知）へ直接移る経路は、いまのモニターにない。この仕様では作らない。
- 切り替えで戻ったときに、モニターのタブの選択や、判断の画面の開閉を保つことは求めない。

## 3. API（R-067）

### 3.1 契約

| method | path | query | 上限 |
|---|---|---|---|
| GET | `/api/campaigns/<campaign_id>/decision-view` | `view`（`operator` が既定、または `blue`） | 1 MiB |

HTTP の状態と、応答の中身の `status` は、別のものとして扱う。場合ごとの応答は、次の表のとおりとする。

| 場合 | HTTP の状態 | 応答の中身 | 判断の画面が出すもの |
|---|---|---|---|
| 作れた | 200 | `{"decision_view": {...}}` | 画面 |
| `view=blue` | 200 | `{"decision_view": {"status": "withheld", "reason": "評価情報はBlueに非公開"}}` | 理由の文 |
| Campaign がない | 404 | `{"error": "not_found"}` | 「この Campaign は見つかりません」と、Campaign を選ぶ画面へのリンク |
| 記録を読めない。評価レポートが壊れている。列の対応が壊れている（3.2 節） | 200 | `{"decision_view": null, "status": "hold", "reason": "記録を確認できません"}` | 理由の文 |
| 応答が 1 MiB を超える | 500 | `{"error": "response_too_large"}` | 「件数が多く、この画面では出せません」 |
| `view` が `operator` でも `blue` でもない | 400 | `{"error": "bad_view"}` | 判断の画面からは起きない |
| 同じ名前の query が 2 つある | 400 | `{"error": "duplicate_query"}` | 判断の画面からは起きない |
| GET と HEAD 以外 | 405 | `{"error": "method_not_allowed"}` | 判断の画面からは起きない |

- 成功の中身は、`decision_view/schema/decision-view.schema.json`（`aym.decision-view/1`）の形とする。3.3 節の項目を足す。
- 調べる順は、既存の経路と同じにする。query の重複、メソッド、Host と Origin、`view` の値、`view=blue`、Campaign があるか、の順である。
- `view=blue` のときは、Campaign があるかを調べる前に返す。Campaign があってもなくても、同じ応答になる。`/api/campaigns/<campaign_id>` の Blue の応答と同じ扱いである。
- `hold` は、`/api/campaigns/<campaign_id>/assessment` と同じ形である。空の一覧を成功として返さない。
- `view` のほかの query は読まず、あっても無視する。

### 3.2 中身の作り方

- 作る関数は、いまの `decision_view/tools/aym_decision_view.py` の `build_view()` を使う。出す項目は、スキーマにある項目だけとする。課題の `extensions`、証跡の参照、プロンプト、ログは出さない。
- 課題は、`finding_id` の重複を除いて数える。同じ `finding_id` が複数あるときは、記録の並びで最初のものを使う。`/api/campaigns/<campaign_id>` の `findings` と同じ規則である。一覧を作るとき、件数を数えるとき、前回と比べるときのすべてで、この規則を使う。いまの `_load()` は重複を除いていないので、ここは直す。
- 評価レポートは、`assessment.load_report()` で読む。モニターの評価タブと同じ読み方である。
- 悪用の情報（KEV と EPSS）は、課題ごとに決める。評価レポートにその課題の記録（`enrichment`）があれば、それを使う。なければ、課題に付いた記録を使う。どちらもなければ数えず、その旨を画面に出す。
- KEV は、記録の状態が `listed` のものが 1 つでもあれば、「悪用が確認されている」とする。EPSS の値が複数あるときは、最大の値を使う。
- 期限切れ（`expired`）、取得の失敗（`missing`、`corrupt`）、未照合（`not_tested`）の記録は、悪用がないものとして扱わない。4.3 節の添える文で、悪用の情報が古い、または付いていない、と出す。
- 前回の Campaign は自動で選ぶ。選び方は、いまの `pick_previous()` のとおりとする。当てはまる Campaign がないときは、比べない。選び方を変える query は足さない。
- 列の対応（状態、番号、期限の列名と、状態の言葉の対応）は、workspace の `decision-view/mapping.json` から読む。ファイルがないときだけ、同梱の既定（`decision_view/tools/mapping.example.json` と同じ中身）を使う。次のどれかに当たるときは、`hold` を返し、黙って既定に切り替えない。ファイルがシンボリックリンクである。1 MiB を超える。厳格な JSON として読めない。形が違う（`fields` と `status_values` がオブジェクトでない）。同梱の既定を読めない。
- 応答は、呼ばれるたびに作る。作った結果をためておく仕組みは足さない。

### 3.3 `aym.decision-view/1` に足す項目

どれも省いてよい項目として足す。前に作った JSON は、そのまま読める。

| 項目 | 中身 |
|---|---|
| `campaign.status` | Campaign の段（AYM の値のまま） |
| `assessment.present` | 評価レポートがあるか |
| `assessment.historical` | 評価レポートが、いまの対象のバージョン（`target_version`）より前のものか |
| `assessment.coverage` | 類型の数。`executed`（実施済み）、`not_executed`（未実施）、`failed`（実行失敗）の 3 つ |
| `items[].assessment_status` | 評価の状態。`confirmed`、`candidate`、`refuted`、`retested`、`proposed`、`undetermined`、`historical`、`unknown` のどれか。評価レポートにその課題がなければ `null` |

### 3.4 大きさの参考値

起草者の手元の Campaign（課題 266 件、前回あり）では、応答は約 140 KB、作るのに約 5 秒かかった。測った値であり、保証する値ではない。同じ割合なら、1 MiB に届くのは 2,000 件ほどである。

## 4. 判断の決まり（R-069、R-070）

### 4.1 課題の状態

| 場合 | 画面に出す状態 | 終わっているとみなすもの |
|---|---|---|
| 評価レポートに、その課題がある | 評価の状態を、モニターと同じ言葉で出す（確認済み、候補、反証済み、再検証済み、修正提案、判定不能、古い証跡、未確認） | 再検証済みと反証済みだけ |
| 評価レポートがない、またはその課題が入っていない | 「未評価」と出す。取り込んだ元の状態があれば、その言葉も出す | 元の状態が、列の対応で `done` か `wont_fix` に当たるものだけ |

- 上の表で「終わっている」に当たらない課題は、すべて「終わっていない」に数える。元の状態がない課題と、列の対応にない言葉の課題も、ここに入る（D-066）。
- 評価の状態の導き方は、モニターの `deriveFindingStatus()` と同じにする。次の行動の文は、モニターの `nextActionFor()` と同じにする。
- 同じ決まりを 2 か所（モニターの HTML と、JSON を作る関数）に持つ場合は、同じ入力の表で両方を動かし、結果が一致することを試験で確かめる（T41）。
- 評価レポートが古い（`assessment.historical` が真）ときは、その評価レポートのすべての課題の状態を「古い証跡」とする。もとが再検証済みや反証済みでも、終わっているに数えない。
- 再検証済みは、再検証が成功したことだけを意味する。運用への反映と承認は別である（SPEC-ASSESSMENT 1.3 節）。画面には「運用への反映は、別に確かめてください」と添える。
- 評価レポートと、取り込んだ元の状態の両方があるときは、評価の状態を使う。元の状態は、課題を開いたときに「元のデータでの状態」として出す。

### 4.2 いま決めること、早めに対応すること

| 段 | 入るもの（終わっていない課題のうち） |
|---|---|
| いま決めること | 次のどれか 1 つに当たるもの。悪用が確認されている（KEV）。評価の状態が確認済み、または修正提案である。未評価で、元の状態が判断待ちである |
| 早めに対応すること | 上に入らないもののうち、次のどちらかに当たるもの。期限を過ぎていて、重大度が重大か高である。悪用の見込み（EPSS の最大値）が `epss_high` 以上である |

課題ごとに、急ぐ理由を言葉で出す。当てはまるものをすべて出す。色は、言葉に添えるだけとする。

| 理由 | 出す言葉 |
|---|---|
| 悪用が確認されている（KEV） | 「悪用が確認されている」 |
| 評価の状態が確認済み、または修正提案 | 評価の状態の言葉と、次の行動の文 |
| 未評価で、元の状態が判断待ち | 「判断待ち」 |
| 期限を過ぎた | 「期限を N 日過ぎた」 |
| 期限が近い（`due_soon_days` 以内） | 「期限まであと N 日」。当日は「期限は今日」 |
| 悪用の見込みが `epss_high` 以上 | 「悪用の見込み N%」 |

- どちらにも入らない終わっていない課題は、「すべての課題」に出す。
- 段を決めるのに、CVSS の点数は使わない。重大度は、期限切れと組み合わせたときだけ使う（R-056、D-068）。
- 並びは表示の目安であり、業務の優先度として記録しない。言葉の説明に、「業務への影響は、担当者が決めます」と書く。
- 並びの重みは、いまの `decision-core` の `assess()` を引き継ぐ。評価の状態が確認済み、または修正提案の課題は、判断待ちと同じ重みにする。

### 4.3 先頭の文

先頭の 1 枚は、上から順に当てはまったものを出す。

| 場合 | 見出しの文 |
|---|---|
| いま決めることが 1 件以上ある | 「いま決めることは N 件、終わっていない課題は全部で M 件です」 |
| いま決めることはないが、終わっていない課題がある | 「急いで決めることはありませんが、終わっていない課題が M 件あります」 |
| 終わっていない課題はないが、下の添える文が 1 つ以上ある | 「終わっていない課題は記録にありませんが、確かめていないことがあります」 |
| 終わっていない課題がなく、添える文もない | 「終わっていない課題はありません」 |

N は、4.2 節で「いま決めること」に入った課題の件数である。M は、4.1 節で終わっていないに数えた課題の件数である。

見出しの下に、当てはまるものをすべて添える。

| 場合 | 添える文 |
|---|---|
| 評価レポートがない | 「この Campaign には評価の記録がありません。検査の範囲は分かりません。取り込んだ元の状態で並べています」 |
| 評価レポートが古い（`assessment.historical` が真） | 「評価の記録は、対象が変わる前のものです。いまの状態は確かめ直してください」 |
| 未実施、または実行失敗の類型がある | 「検査していない範囲が K 類型あります。安全とは限りません」 |
| Campaign の段がレビュー待ち | 「この Campaign は、人のレビューを待っています。モニターで確かめてください」 |
| 悪用の情報が古い、または付いていない | いまの画面の注意書きを引き継ぐ |

- 「終わっていない課題はありません」は、添える文が 1 つもないときだけ出す。添える文は、見出しのすぐ下に、本文と同じ大きさで出す。

### 4.4 進捗率を出さない

- 片付いた割合（%）と、片付いた割合を表す帯は出さない。いまの画面の「N 件のうち M 件が片付いています（40%）」と、その下の帯は取り除く。
- 悪用の見込み（EPSS）の % は、記録された値なので出す。
- 状態ごとの件数は出す。順は、終わっていない状態を先にする。
- 「前回から N 件が片付いた」のような、前回との差の件数は出す。実記録値だからである。

## 5. 判断の画面（R-066、R-068）

### 5.1 引き継ぐもの

中身は、いまの `decision_view/web/decision.html` を引き継ぐ。先頭の 1 枚、いま決めること、早めに対応すること、前回から変わったこと、すべての課題、言葉の説明である。ファイルを選んで読む使い方と、`?data=` で JSON を読む使い方も残す。`?data=` に指定できるのは、判断の画面と同じ配信元のパスだけとする。ほかの配信元の URL と、`file:` や `https:` で始まる URL は、読まずにエラーの文を出す。いまの画面と同じ決まりである。

見た目は、いまの色と書体のままとする（D-062）。モニターの見た目の決まりは当てない。色だけで区別しないこと、キーボードで操作できること、フォーカスが見えることは守る（D-067）。

### 5.2 足すもの、変えるもの

1. 切り替え（2 節）。
2. Campaign を選ぶ画面（5.3 節）。
3. 課題を開いたときの「モニターでこの Campaign を見る」。
4. API の応答の読み取り。`decision_view` の包みを外して読む。`status` が `withheld` または `hold` のときは、理由を文で出す。件数も一覧も出さず、片付いたと読める文も出さない。
5. 判断の決まり（4 節）。状態、次の行動、先頭の文、進捗率の取り除きである。
6. 課題を開いたときの中身に、評価の状態と次の行動を足す。評価の詳細（分類、CVSS、業務影響、再検証のチェック）は出さず、モニターへ案内する。

### 5.3 Campaign を選ぶ画面

- `/decision` を `campaign` も `data` も付けずに開いたときに出す。
- `/api/campaigns` を読み、Campaign を新しい順に並べる。出すのは、名前（`intent_id`）、作った日時、課題の件数、状態である。
- 状態の言葉は、モニターの言葉をそのまま使う（作成済み、レビュー待ち、完了、未完了など。`index.html` の状態の表が正である）。
- 選ぶと、`/decision?campaign=<campaign_id>` を開く。
- 読み込み中、0 件、取得の失敗を、それぞれ言葉で出す。
- `campaign` に、ない Campaign を指定して開いたときは、「この Campaign は見つかりません」と出し、Campaign を選ぶ画面へのリンクを出す。

### 5.4 AYM の外で開いたとき

- AYM のサーバーから配られているかは、`GET /api/health` で見分ける。200 で `{"status": "ok"}` が返ったときだけ、AYM のサーバーとみなす。エラー、404、5 秒以内に返らない場合、ほかの中身の場合は、すべて AYM の外とみなす。
- AYM の外では、いまと同じ動きにする。切り替えと、Campaign を選ぶ画面は出さない。
- AYM の外で `campaign` が付いているときは、API を呼ばない。「この開き方では Campaign を読めません。JSON のファイルを選んでください」と出し、ファイルを選ぶ画面を出す。

### 5.5 読み直し

- 判断の画面は、自動では読み直さない。開いたときと、「読み直す」を押したときだけ読む。読んでいる途中で文が入れ替わると、判断の妨げになるためである。
- データを作った時刻は、いまと同じく画面の下に出す。

### 5.6 内部の名前

- `campaign_id`、`finding_id`、状態の内部値、API の名前は、「技術の詳細」と名づけた折りたたみの中だけに置く。最初の表示にも、課題を開いたときの表示にも出さない。
- Campaign の名前には `intent_id` を出す。人が付けた名前が、ほかにないためである。要件（R-068）でも、内部の名前に数えない。

### 5.7 最初に出す量

## 6. モニター側の変更（R-064、R-065）

- 入口に案件一覧と選択した案件の検知を並べる。狭い画面では案件の選択欄の下に検知を置く。証跡、判断の各リンクは選択中の案件を開く。案件のタブ、15 秒ごとの更新、DOM の差分更新を使う。

## 7. 置き場所

パッケージに入る HTML は、`ai_yori_murasaki/web/*.html` だけである（`pyproject.toml` の package-data）。いまの `decision_view/web/decision.html` は、インストールした環境では配れない。そこで、HTML を 1 か所だけに置くことにして、次のように分ける。

| 置くもの | 置き場所 |

| 配る HTML | `ai_yori_murasaki/web/decision.html` |

`decision_view/web/decision.html` は置かない。同じ HTML を 2 か所に持たないためである。`decision_view/README.md` の手順は、新しい場所に合わせて直す。

## 8. 安全と互換

- 追加する経路と API は、GET と HEAD だけを受ける。記録へ書き込む処理を持たない。
- loopback だけで配ること、Host と Origin の検証、任意のパスを配らないこと、出来事の記録のファイル（`events.jsonl`）と CAS のオブジェクトをそのまま配らないことは、既存の決まり（API-CONTRACTS 2 節）のままとする。
- 既存の API の応答と、`schemas/v1/` のスキーマは変えない。`aym.decision-view/1` は、3.3 節の項目を足すだけとする。
- CLI での書き出し（`aym_decision_view.py`）は残す。API と同じ関数で作るので、同じ中身になる。
