### 0.3 言葉

- 判断の画面: 結果を読んで、何を先に決めるかを判断する人のための画面。いまは `decision_view/` にある。
- モニター: エージェントを動かす人（オペレーター）のための画面。いまは `ai_yori_murasaki/web/index.html` にある（R-044）。
- 課題: AYM の Finding 1 件。同じ原因への複数の試行は、1 件として数える（R-051）。
- 評価の状態: 評価レポート（[SPEC-ASSESSMENT](SPEC-ASSESSMENT.md)）から導く課題の状態。モニターの評価タブに出ている、確認済み、候補、反証済み、再検証済み、修正提案、判定不能、古い証跡、未確認の 8 つである。
- 未評価: 評価レポートに、その課題が入っていないことを示す表示。評価の状態の 1 つではない。
- 技術の詳細: 判断の画面で、内部の名前を置く折りたたみ。課題を開いただけでは開かない。

## 1. 追加要件

### R-064 判断の画面とモニターの両立
- 根拠: U（U1、U4、U6、U7）。R-044 と R-057 の具体化。
- 義務: MUST
- 内容: 製品は、判断の画面とモニターの両方を備える。どちらも、同じサーバーから開ける。片方を、もう片方の代わりにしない。
- 受入条件: モニターを配るサーバー（`aym monitor serve`）から、ほかに何も起動せずに判断の画面を開ける。モニターの既存の機能は変わらず、既存の API の応答（状態コードと JSON の中身）は変更の前と同じである。モニターの画面に足すのは、切り替えと、参照 API の説明の 1 行だけである。既存の試験が通る。
- 依存: R-044, R-057
- v1対象: v1

### R-065 同じ対象を保った行き来
- 根拠: U（U7）
- 義務: MUST
- 内容: 2 つの画面は、切り替えの操作で行き来できる。Campaign を開いているときは、相手側でも同じ Campaign が開く。切り替えは、どちらの画面でも、ページの先頭に、同じ言葉で置く。
- 受入条件: モニターの Campaign 詳細から 1 回の操作で、判断の画面の同じ Campaign が開く。逆向きも同じである。Campaign を開いていないときは、相手側の最初の画面が開く。切り替えはキーボードだけで操作できる。
- 依存: R-064
- v1対象: v1

### R-066 オペレーターの機能はモニターが受け持つ
- 根拠: U（U4、U7）
- 義務: MUST
- 内容: Run、出来事、評価の詳細、RSI、承認、モデルと接続先の状態、資料は、モニターで扱う。判断の画面に、これらを作り直さない。全部を見る手段はモニターとする。判断の画面は、詳しく見たい人をモニターの同じ Campaign へ案内する。
- 受入条件: 判断の画面に、Run の一覧、出来事の一覧、評価の詳細、RSI の表、承認の操作がない。判断の画面のどの Campaign からも、モニターの同じ Campaign へ移れる。
- 依存: R-044, R-064, R-065
- v1対象: v1

### R-067 判断の画面は同じ記録の投影
- 根拠: 案（R-009、R-057、R-060、API-CONTRACTS 2 節を判断の画面に当てはめたもの）。Task 20261116-01 の Constraints（公開境界を変えない、書き戻さない）を引き継ぐ。
- 義務: MUST
- 内容: 判断の画面は、モニターと同じ記録を、読み取りだけの API で受け取って出す。画面から記録へ書き戻さない。Blue の表示（`view=blue`）では中身を出さない。課題の件数（状態によらない全件。`finding_id` の重複を除く）は、同じ Campaign についてモニターと食い違わない。
- 受入条件: 追加する API は GET と HEAD だけを受ける。`view=blue` では、件数も名前も含まない応答を返す。同じ Campaign で、判断の画面の課題の件数が、モニターの検知の件数と一致する。判断の画面を開く前と後で、Store の中身が変わらない。
- 依存: R-009, R-057, R-060
- v1対象: v1

### R-068 判断の画面の表現
- 根拠: U（U1、U2、U3、U5、U8）。R-057 の具体化。
- 義務: MUST
- 内容: 判断の画面は、最初の表示で、いま決めることを文で示す。課題を単位にして、急ぐ順に並べる。内部の名前（ID、状態の内部値、API の名前）は、「技術の詳細」の中だけに置く。最初の表示にも、課題を開いたときの表示にも出さない。Campaign の名前として出す `intent_id` は、内部の名前に数えない。色だけで区別せず、言葉を添える。最初に出す量を絞り、残りは開くと読める形にする。見た目は、やわらかい調子（いまの判断の画面の色と書体）のままとし、モニターの見た目の決まりは当てない。
- 受入条件: 幅 1440px と 390px の最初の表示に、決めることの件数を言う文と、モニターへの切り替えが入る。最初の表示と、課題を開いたときの表示に、内部の名前が出ない。状態と急ぐ理由が、色に加えて言葉で出る。キーボードだけで、すべての操作ができる。
- 依存: R-057, R-060
- v1対象: v1

### R-069 判断の画面は評価の状態を使う
- 根拠: U（U10）。R-057（説明層は評価層の投影であり代替しない）と R-060 の具体化。
- 義務: MUST
- 内容: 評価レポートがある課題では、判断の画面は、評価の状態と次の行動を、モニターと同じ言葉、同じ導き方で出す。評価レポートがない課題は「未評価」と示し、取り込んだ元の状態を使う。状態が分からない課題は、終わっていない側に数える。検査していない範囲があるとき、または検査の範囲が分からないときは、安全と読める表示にしない（R-051）。安全と読める表示とは、残りがないことだけを言い、検査していない範囲に触れない表示を指す。
- 受入条件: 同じ課題について、判断の画面の状態と次の行動が、モニターの評価タブと一致する。評価レポートがない課題に「未評価」と出る。状態が分からない課題だけの Campaign で、「終わっていない課題はありません」と出ない。未実施の類型がある Campaign で、その類型の数と「安全とは限りません」が出る。
- 依存: R-051, R-055, R-057, R-060, R-067
- v1対象: v1

### R-070 進捗率を出さない
- 根拠: U（U9）。FRONTEND-DESIGN 0 節（進捗率・完成率は作らない）を判断の画面にも当てる。
- 義務: MUST
- 内容: 判断の画面は、片付いた割合（%）と、片付いた割合を表す図を出さない。悪用の見込み（EPSS）のような、記録された値の % は、これに当たらない。残っている件数を、先頭の見出しの文で言う。終わっていない課題が 1 件でもあるときは、片付いたと読める表示にしない。件数は実記録値だけを出す。
- 受入条件: 判断の画面に、片付いた割合の数字と、片付いた割合を表す帯がない。終わっていない課題があるとき、先頭の見出しの文にその件数が出る。
- 依存: R-068, R-069
- v1対象: v1
