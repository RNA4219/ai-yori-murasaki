# 案件の表示・比較・受付連結の仕様

[要件 R-081〜R-085](REQUIREMENTS-CASE-DECISIONS.md) を、既存の記録を読める状態で追加する。

## T53　修正後の再検証

現行の評価に再検証結果があれば、成功・失敗・判定不能を修正案より先に表示する。失敗時は「再検証失敗」と示し、失敗した検査と修正内容の見直しを案内する。未完了の課題に数える。旧版の評価には古い証跡の表示を優先する。判断画面のJSON、画面上のラベル、モニターの評価欄で照合する。

## T54　前回との差

各回の重複を課題IDで除き、同じIDを優先して比較する。同じ場所を指す別IDをファイルパスだけで結び付けない。従来の原典情報で同じ課題を一意に特定できる入力は引き続き比較できる。前回 A・B、今回 B・C の例に加え、並び替え、同じ記録の再送、状態変更も確認する。消失は今回の記録に存在しないことだけを表す。

## T55　課題と観測の照合

operatorが課題を取り込み、照合用の観測が0件なら、判断画面に照合待ちの課題数と、資源一覧または検知の観測を取り込む案内を出す。観測を取り込んだ場合は現在の照合結果と理由を表示する。取得エラーは再取得の案内を表示する。Blueの非公開応答から件数や観測の有無を開示しない。

## T56　受付と監査の連結

操作者は `aym intake link --receipt-id <受付ID> --campaign-id <案件ID>` で同一ワークスペースの既存監査を指定する。1件の受付が指す監査は1件。同じ組の再送は成功する。別の監査への上書きや不明なIDの指定は失敗し、元の対応を保つ。検索APIと受付台帳に対応先を表示し、受付から監査結果を開けるようにする。未連結の表示は監査の実施状況を推定しない。過去の受付も検索できる。閲覧で台帳を更新せず、同名受付、登録再送、Blueの非公開を維持する。

## T57　製品の類型別検証範囲

判断画面から読める一覧に、認可不備、SQLインジェクション、XSS、パストラバーサル、既知依存脆弱性の5行を置く。各行に固定データでの評価と、実モデル・Dockerでの修復後の再検証を示す。前者は5類型で確認済み、後者は認可不備で確認済み、ほか4類型は未検証である。製品検収の記録日と根拠を示し、個々の案件の検査結果とは区別する。この表示のために新たな実ラボ試験を行う必要はない。
