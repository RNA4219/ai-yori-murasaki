# 追加検証の実装計画

## 前提と必要性

P0で計測単位、P1で実行方策の追跡を揃えたうえで進める計画である。今回の成果物は設計とTaskであり、以下の追加実装と実験は行わない。実装開始には既存の追加実装承認規約に従う。

| 対象 | 必要な理由 | 実装可能性と不足 |
| --- | --- | --- |
| SQLiの実LLM修復 | 現在の認可不備の実行経路と、他類型の固定fixture採点を区別して検証するため | SQLiシナリオ資産はあるが、実修復の実行契約と独立Oracleの追加が必要。難度は中。隔離DBと正常機能の正解を先に用意する |
| 実WazuhイベントのBlue評価 | 保存済みイベントの取り込み成功だけでは、検知・調査が正しいか分からないため | 意味保持の正規化イベントはあるが、Blue入力はHTTP telemetryが中心。専用の入力契約・参照権限・正解集合が必要。難度は中。Indexer接続は別途必要性を判断する |
| 異なるRSI候補の比較 | 過去の実比較では候補が不変、外部故障pairもあり、改善を実証していないため | 方策bundle、freeze、比較、通常実行への接続は使える。モデルの版固定と利用枠、計測不良を除いたtrain出典、未見集合が不足。難度は中〜高 |

## A. SQLiの隔離ラボ修復

[Task 20261109-02](../tasks/TASK.p2-sqli-11-09-2026.md)で扱う。最初の1類型をSQLiに限定し、対象・DB・リクエストは外部へ到達できないローカルDockerラボ内に置く。Oracleの期待値と正解コードはRed／Blue／Purpleへ渡さない。

1. 原因を持つtrain fixture、調整後のvalidation、未見のholdoutを分ける。構文差だけの複製を未知問題への汎用能力と呼ばない。
2. Redの実アクセス、Blueの観測に基づく検知、Purpleのコード参照・原因分析・修正案生成を、それぞれ発行済み証拠へ結ぶ。
3. brokerが許可した対象ファイルだけへ修正を適用する。SQLのパラメータ化など、生成された実差分を保存する。固定置換を実LLM修復の成果に数えない。
4. 修正前の攻撃成立、修正後の同じ攻撃の不成立、正常検索・空結果・引用符を含む合法入力・許可された更新などの回帰を独立した非LLM Oracleで判定する。HTTP statusだけでSQLiの不成立を断定せず、実際の返却レコード／DB状態を検査する。
5. Oracle自体に脆弱・正常・過剰修復・未実行の対照を与え、正しい判定ができることを先に確認する。通信失敗、DB未起動、未適用を攻撃遮断成功にしない。

実装前に操作契約、正解の秘匿、停止予算、評価manifestを固定する。最初は決定的試験で経路を確認し、実LLM／実Dockerの結果は別記する。成功の主張は、実行した固定fixtureと未見fixtureのID・件数・修復差分・Oracleの判定範囲に限定する。

## B. 実WazuhイベントのBlue評価

[Task 20261109-03](../tasks/TASK.p2-wazuh-blue-11-09-2026.md)で扱う。ユーザーが認可したローカル環境の、明示指定した保存済み実アラートから始める。取り込みをAPI検索成功と呼ばない。`agent_id→role`、rule levelからHTTP statusを生成する等の擬似値変換を使わない。

正規化eventと原観測CASの参照を保持するBlue入力契約を設計する。rawの秘密・個人情報を除去し、必要な観測フィールドと原観測のhashを保持する。モデルへ渡す前に、ローカル環境から外へ送れる情報を確定する。外部送信を認めない資料はローカルモデルで扱う。

イベントの正解はBlueの回答から独立して作る。検知すべき攻撃、正常、調査が必要だが確定不能なものを分け、ラベル不明のイベントを正常として扱わない。重複した取り込みと、異なる実事象を区別し、CAS参照とイベントの識別規則を事前に固定する。ラベルの見直しで結果が変わった場合は変更履歴を残す。

| 指標 | 分母・記録 |
| --- | --- |
| recall | 検知対象と独立に確定した事象。未検知も含む |
| precision／誤検知 | 提出findingの事象照合結果。正常を攻撃とした件数を併記 |
| 証拠参照の正確性 | 参照の存在、所有権、対象事象・観測フィールドとの一致。不正参照は拒否して別計数 |
| 調査コスト | イベント／findingあたりのモデル呼び出し、token、経過時間、人の確認時間。未完了も記録 |
| 完了性 | 対象イベント数、除外数と理由、ラベル不明数、通信・形式・参照エラー数 |

train／validation／holdoutは同じ実事象の派生アラートが境界をまたがないよう分ける。採点の正解はモデルとExperience Memoryから分離する。現在の実ログ187件の取り込み記録から、この評価の数値を作らない。

## C. 有効なRSI改善実験

[Task 20261109-04](../tasks/TASK.p2-rsi-experiment-11-09-2026.md)で扱う。測定修正前の失敗を、Blueの能力不足とみなしてそのまま学習・採用へ戻さない。影響が疑われるtrain出典を隔離し、P0修正後のrunnerとOracleで再測定してから使う。旧版のrunner hashを持つfreezeは継続使用しない。

baselineとcandidateのcanonical hashが異なることに加え、仮説に対応するprompt・探索規則・予算等の実差分と、実行中にその方策が使われた証跡を確認する。versionだけを変えた候補や不変候補は改善実験に進めない。

比較前に、目的、source／runner／dataset／model／policyのhash、split、seedの対、初期化、経験snapshot、呼び出し・時間予算、反復数、主指標、非劣化基準、停止条件、負の対照をmanifestで固定し、preflightを通す。trainだけで候補を調整し、凍結後のvalidationとholdoutは調整に使わない。観測後に調整した場合は別の未見holdoutを用意する。

同じ条件で対比較し、目的達成、検知の誤り、修復、正常機能、費用、停止理由を独立Oracleで採点する。外部故障は影響pairと診断証跡を保存し、比較不能を改善成功やgainゼロの正常測定に置き換えない。candidate由来の失敗は損失として残す。除外が残る状態では採用を進めず、条件を事前に固定し直した別実験で確認する。

実測artifactとpostrunが揃ってから採否を判断する。unpinned cloud aliasは探索結果として報告し、既存の採用ゲートを通過したと扱わない。採用する場合はreview→apply→通常実行のbundle hash照合→rollback確認まで別々に記録する。今回のCLI fixture試験の仮の成功結果を、実モデルの比較結果へ流用しない。
