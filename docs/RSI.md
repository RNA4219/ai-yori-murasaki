# RSI（再帰的自己改善）

本プロジェクトに組み込む自己改善の方針を定める。以下の9項目はユーザーが提示した整理を収録したもので、参照資料の逐語引用ではない。
この方針に従う実行器・決定的評価器・Experience Memoryを実装した。操作は[製品ガイド](PRODUCT-GUIDE.md#rsiの操作)、実証範囲は[製品検収](acceptance/AC-20261106-06.md)を参照する。ローカル認可方針の比較結果を、LLMの汎用性能向上の証明には使わない。

## 目的と基本の流れ

目的は、エージェントの実行結果から改善候補を作り、旧版との比較で効果を確かめ、確認できた改善を次の実行へ引き継ぐこと。

実行 → 証拠の保存 → 原因分析 → 改善候補の作成 → 同条件比較
→ 未見課題での確認 → 採用判断 → 次の改善

## エージェントRSIのモデル固定とno-op候補（2026-11-11）

`train` でcandidateのbundle digestがbaselineと同一だった場合、`compare` は開始前に拒否する。validation／holdoutの実行も、holdoutアクセス監査も発生させない。

モデルの固定は `model_pinning.status` の自己申告ではなく、凍結した `expected_models` と実行観測を照合する。例：

```json
{"model_pinning":{"status":"pinned","note":"local Ollama",
  "expected_models":{"model-name:tag":"sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}}}
```

値は `GET /api/tags` で確認したローカルモデルのdigestをfreeze**前**に設定する。train・validation・holdoutの各実行で、要求モデル名、LLM応答に含まれるモデル名、`/api/tags` の前後digestの一致を確認する。証跡の欠落、モデルの不一致、OpenAI互換API（DGX等）のモデル名、Ollama cloud aliasは `exploratory-unpinned-model` とする。既存の `{"status":"pinned","note":"..."}` は受け付けるが、digestの事前固定が無いので採用準備完了にはしない。

`/api/tags` の前後確認は、ローカルOllamaサーバーの自己申告を信頼する運用上の確認であり、推論時に実ロードされた重みの暗号学的な証明ではない。モデル名・digestを偽装できる実行器やサーバーに対する保証、実モデルの性能改善の証明には使わない。対応：[Task 20261111-01](tasks/TASK.agent-rsi-pin-11-11-2026.md)／[AC-20261111-01](acceptance/AC-20261111-01.md)。

## 1. 目的と評価条件を先に固定する

何を達成すれば成功か、何を測るか、どこまで実行してよいかを決める。
評価対象、予算、反復回数、停止条件、採用基準は、評価結果を見る前に固定する。
作業量やツール呼び出し数だけを成功指標にしない。

## 2. 旧版と改善候補を分ける

旧版をbaseline、改善候補をcandidateとして管理する。
コード、設定、プロンプト、入力、モデルなどの識別情報を記録し、
どの変更を評価しているのか追跡できるようにする。

## 3. 実行結果を証拠として残す

実行した操作、観測結果、仮説、支持・反証、拒否理由、
停止理由、使用予算、完了状態を保存する。
モデルの「成功した」「改善した」という自己申告だけでは採点しない。
記録の完全性を検証し、秘密情報は保存前に除去する。

## 4. 失敗の原因から改善候補を作る

失敗を入力形式、探索方針、状態管理、ツール制約、予算、
実行環境などに切り分ける。
記録から原因を確認し、プロンプト、探索方針、コード、
設定などの改善候補へ変換する。
まずオフライン確認や回帰テストを行い、必要な実行評価へ進む。

## 5. 実行中も観測に応じて方針を更新する

仮説を立て、仮説を区別できる操作を選び、結果を観測する。
証拠に応じて仮説を支持・反証し、進展がなければ別の仮説へ移る。
同じ拒否や低信号の操作を無目的に繰り返さない。
回復可能な作業と残予算がなければ、理由を残して停止する。

## 6. 同じ条件で旧版と比較する

baselineとcandidateを同じ対象、同じseed、同じモデル条件、
同じ予算で実行する。対象の初期状態も揃える。
seedごとの結果の差を比較し、成功だけでなく、
誤検出、見逃し、完了状態、費用、安全性も確認する。
未完了や通信障害のある実行は、性能比較から除外し、診断用に残す。

## 7. 改善用と評価用の課題を分ける

trainでは原因分析と候補の調整を行う。
調整を止めた候補をvalidationで比較し、
最後に未観測のholdoutで劣化していないか確認する。
holdoutを見た後で候補を変更した場合、
その課題は診断用とし、採用評価には別の未見課題を使う。
正解情報はエージェントへ渡さない。

## 8. 経験を次の実行へ引き継ぐ

任意のExperience Memoryでは、完了したtrain実行から、
支持・反証・方針転換・未検証の結果を抽象カードとして保存する。
対象固有の本文や資格情報などは含めない。
次の実行では関連する経験だけを取り出し、計画材料として使う。
過去の経験を、今回の対象で成立した証拠として扱わない。
評価中に経験集合が変わらないよう、読み込む集合を固定する。

## 9. 採用判断と反映を分ける

事前に決めた改善基準と品質条件を満たした候補だけを採用候補にする。
評価結果に合わせて閾値を後から緩めない。
promotion-readyはレビュー待ちの状態であり、
既定の実行器への反映は別の操作として扱う。
採用・不採用の理由を記録し、次の改善へつなげる。

## 適用上の注意

参照資料で扱う採用評価器はfinding recallを中心に評価する。
目的そのものの達成を改善したい場合は、
その達成を検証できる評価器と採用基準を別途揃える。
既存案件の反復回数や数値閾値は、別用途へそのまま流用しない。
機能の実装完了と、性能向上の実証は分けて扱う。

## 本プロジェクトへの適用

Blue / Purple 基盤で将来 RSI を実装・評価するときは、以下の対応を用いる。具体的な閾値・反復回数・評価器は各 Task で事前に定める。

| 対象 | 改善を判定する根拠 | 評価の扱い |
| --- | --- | --- |
| Red | 認可された目的の達成と、独立した Oracle による確認 | finding recall の増加だけで目的達成としない |
| Blue | 検知の誤検出・見逃し、調査・修復の結果、正常系への影響 | 検知改善と修復成功を対応する評価器で確かめる |
| Purple | 検知・修復の不足に対する改善と、旧版との差 | 調整用の攻撃・ログを未見の採用評価へ流用しない |

実行中の仮説更新は、固定された方策の中で行う適応とする。評価中にコード、プロンプト、モデル条件、読込み済み経験集合を差し替えて別 candidate にしない。
同じ seed は比較条件の一部であり、モデル応答や実行環境まで完全に同じになる保証とはしない。対象の初期化方法と残る非決定性も記録する。

未完了・通信障害等の比較に受理できない run は、理由と影響した pair を隔離して診断に残す。完了した不成功を都合よく除外しない。
除外件数、停止理由、完了率、費用、安全性も報告し、candidate 由来の停止や障害を比較集合からの除外で隠さない。

Experience Memory は任意とし、無効な評価でもその状態を記録する。使用する場合は完了した train 実行だけから抽象カードを作り、validation / holdout の観測や正解を記憶へ戻さない。
評価用の経験 snapshot と取得規則を固定し、対象固有の運用記憶を採用評価へ混ぜない。
参照資料の operational lane にある対象固有 precedent は、今回採用する抽象カードとは別機能であり、移植・利用しない。

作業の段取りは [RUNBOOK の RSI](../RUNBOOK.md#rsi)、記録項目は [RSI 契約](CONTRACTS.md#rsi)、検収条件は [EVALUATION](../EVALUATION.md#rsi-documentation-criteria) に接続する。
