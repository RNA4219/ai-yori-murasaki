# 完全監査の計画

完全監査を開始する前に読む。個別調査を自動で完全監査に広げない。元のSKILL.mdの「Full audit planning」を切り出したもの。実行・保存・出力先・共有ファイルの所有権は[EXECUTION-SAFETY.md](EXECUTION-SAFETY.md)に従う。

## 範囲と前回結果

一回で全体を調べ尽くしたと扱わない。[RECONNAISSANCE.md](RECONNAISSANCE.md)の決定的な範囲単位で探索前に台帳を作り、担当から結果を受けるたび親だけが更新する。[HUNTING.md](HUNTING.md)に従って探索漏れを独立点検する。

同じrepoの前回結果がある場合、互換性のあるすべての`coverage-ledger.json`と`findings.json`を計画前に読む。

1. 各レコード・範囲単位の関連ソースを現在と比較する。コミット参照があるだけでは経路が同じ証明にならない。
2. 関連ソース・条件が同じで、証拠が現在の要件にも適合する前回の`confirmed`だけを候補へ引き継ぐ。fingerprintを保持し、現在の`planned`単位へ結ぶ。探索から除くのはその根本原因だけとし、現在の検証工程を通す。工程3で再検証する担当が単位の所有者になり、証拠を加えて`candidate`へ進める。
3. 前回確定の関連ソースが変われば、現在の再検証用`planned`単位を作る。探索の除外リストに入れず、現在の独立検証が成立するまで確定扱いにしない。
4. 前回の`needs_validation`、`deferred`、`blocked`、`out_of_scope`、変更された単位は現在の作業にする。まだ外部事実が不足する要検証も、現在のソース経路を確かめてから同じfingerprintで`planned`単位へ結び、障害を保持する。再検証者の証拠で所有者と`candidate`状態を設定する。これらの前回状態で現在の作業を省略しない。
5. 同じソースの前回`covered`は優先度の参考にできるが、現在の台帳に残す。前回の`rejected`が抑止するのは変わっていない反証済みの主張だけで、単位の探索ではない。証拠が変われば現在の作業にする。
6. 前回のプロファイルと範囲を読む。前回の`quick`や範囲限定結果は記録された証拠と不足だけを引き継ぎ、範囲外の安全を意味しない。

互換性のある前回台帳がない場合は最終報告にその事実を示す。欠落・非互換な台帳を隠さない。使ったパスとソース参照はrun-metadataへ記録する。

## プロファイル

利用者の依頼に合わせて選び、指定がなければ`standard`を使う。規模と重要性から別の候補を提案できる。`run-metadata.json`の`profile`・`scope_paths`と報告書に明記する。

| プロファイル | 探索と独立確認 |
|---|---|
| `quick` | 入口×境界×攻撃クラスへ単位を粗くし、subsystemの正規参照を固定値`profile/quick/all-in-scope-subsystems`にする。探索は正確に1波、その後の最終範囲点検は正確に1回。各候補を発見者と別の新しい検証者が確認し、工程3と5を兼ねる。追加波は起動せず、点検で認めた不足・再割当を`deferred`へ残す。 |
| `standard` | 既存の6工程、各波後の範囲点検と、別担当による最終の不足なし確認を行う。工程3と5は別の新しい検証者が担当する。 |
| `deep` | subsystemとライフサイクルで細分化し、範囲点検が不足なしとなるまで波を重ねる。工程3と5は別の新しい検証者が担当し、`prior_covered_same_source`にも独立した2回目の確認を行う。 |

範囲限定では指定パス、subsystem、分野、2つのソース参照間の差分など、範囲内だけを割り当てる。発見した範囲外は`out_of_scope`に残し、`covered`にしない。`quick`と範囲限定は部分的な診断と明記する。プロファイルで変わるのは広さと重複であり、候補の採否、実行境界、要検証の扱い、スキーマ検査、確定の独立検証を弱めない。

## 厳密な予算ゲート

利用者の予算、または親が大規模対象に提案する予算を、全工程のエージェント呼び出し回数の上限としてrun-metadataへ記録する。未指定はnullであり、勝手な上限を追加しない。おおむね一範囲単位が一探索割当、生き残った一候補がプロファイルに応じて1回または2回の検証になる。

**最初の偵察担当を起動する前**に、基本の偵察4回、`quick`なら波後の最終点検1回、`standard`・`deep`なら波後点検1回と別の最終点検1回、少なくとも検証1回を予約する。追加の重点偵察にも毎回このゲートを繰り返す。上限で最低限を賄えなければ誰も起動せず、上限増額・範囲縮小・プロファイル変更を確認する。条件が変わらなければ`run_status: "incomplete"`、`incomplete_reason: "budget_cannot_fund_reconnaissance_and_reserves"`を記録し、診断を実施していないと報告する。

予算は次の順で扱う。

1. 偵察、各波後点検、別担当の最終点検をすべて呼び出し回数へ計上する。
2. 探索より先に点検と検証分を確保する。`quick`は最終波後点検1回、他は各波の直後点検1回と別の最終点検1回を確保する。候補あたり1回または2回を目安に検証分も確保する。不明な場合は点検を引いた残りの30%を目安にする。どちらの予約分も探索へ回さない。
3. 探索枠の範囲で優先順に割り当てる。各波の直後に予約した点検を実施し、最終点検と検証の予約を残す。
4. 次の波の前にも直後点検を新たに予約する。必須点検と検証分を確保できなければ探索を起動せず、その波の予定単位を`deferred`、理由を`budget_cannot_reserve_critics_and_validation`にする。保持した最終点検で不足を記録する。

第1波の前に、偵察前の見積りを、生成した単位数、探索担当数、必須点検、検証予約、残額による実行可否で更新する。明らかに賄えなければ証拠を薄めず、狭い範囲や粗いプロファイルを提案する。後の判明事項で最終点検の予約を使い切った場合は探索を止め、予定単位を保留し、`incomplete_reason: "critic_budget_exhausted"`として網羅完了を主張しない。

候補の増加や工程5の実質変更で追加検証が必要になる場合も、厳密な上限を黙って超えない。全候補を検証できなければ探索を止め、fingerprint順に可能な分だけ検証し、`incomplete_reason: "validation_budget_exhausted"`で未完了にする。未検証のfingerprintは台帳の`candidate`に理由とともに残す。`findings.json`へ入れず、`needs_validation`への読み替えもしない。部分報告は冒頭で未検証のfingerprintと単位を列挙する。
