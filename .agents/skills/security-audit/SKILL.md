# 脆弱性診断

低信頼の主体が、どの入力・操作によって、誰の資源を守る境界を越え、何を起こせるかをソースから確かめる。影響、根拠、最小の再現、優先度、最小の修正案を返す。監査自体は対象ソースを変更しない。

## 依頼に合う範囲を選ぶ

- **個別調査**：相談、特定箇所のレビュー、候補の切り分けでは関係する指示だけを使う。自動で全工程を開始したり、監査用ディレクトリや報告書を作ったりしない。必要な委任結果は現在の作業へ返す。
- **完全監査**：コードベースの監査・ペンテスト、完全・包括的なレビュー、監査成果物を依頼されたときは下記の6工程をすべて行う。
- どちらの依頼か判断できない場合だけ、完全監査やファイル作成の前に一点確認する。スキルを読んだだけでは実行許可は増えない。

## 常に守る判断・実行条件

ソース閲覧は読み取りに限定する。対象が制御するビルド、テスト、プロセス、ブラウザー、エミュレーター、ファザー、fixture処理を実行する前に、[実行・証跡保全](EXECUTION-SAFETY.md)を必ず読む。OSによる隔離、外部通信遮断、空の許可リスト環境、対象・ツールの読み取り専用化、scratch限定書き込み、CPU・メモリー・プロセス数・ファイルサイズ・ディスク・時間の上限がすべて必要。欠ける場合は実行せず、決定的な不足を要検証として残す。

実データ・実認証情報、稼働中の配備先、外部・共有サービス、他人のデータ、ライブの管理系を調べる通信は行わない。依存物の取得・インストール、公開、リリース変更、有料APIの消費、共有環境の負荷試験は行わない。ローカルのダミー主体・資源で最小の境界違反を観測したら止める。証跡ファイルの保存にも上記参照先の親側昇格手順が必要で、scratchの出力をそのまま証拠にしない。

| 判定 | 必要な根拠と扱い |
|---|---|
| `confirmed` | 完全なソース経路、実在する境界・影響、成立条件、妨げる制御がないこと、隔離した最小の観測結果をそろえる。確定した内容にだけ重大度を付ける。 |
| `needs_validation` | ソースに裏付けられた候補で、配備・実行環境などの決定的な事実が未確認。正確な不足と、それを解く安全なローカル確認または所有者による観察計画を示す。重大度は付けない。 |
| `rejected` | ソース、既存の防御、実測、影響の欠如、成立しない前提によって候補を反証したもの。要検証へ逃がさない。 |

設定上の推測、単なる推奨事項の欠落、本人の権限内の動作、自己影響だけでは脆弱性にしない。防御Aで防げるなら防御Bの欠落は改善メモとする。クラッシュをコード実行へ、単独処理の停止を共有サービスの停止へ読み替えない。ソースにないプロキシ、ブラウザー、IdP、クラウド、配備制御は、存在・不在のどちらも仮定しない。

重大度は成立可能性と実証した影響から決め、総合重大度は影響を超えない。`critical`は未認証からのコード実行・全データストアへのアクセス・任意アカウントの乗っ取り、`high`は認証回避、テナント越境、他人に作用する保存型スクリプト実行、認証後コード実行、未認証の共有サービス停止など、明示的な制御の完全な突破を目安とする。`medium`は影響範囲や成立条件が限られる境界違反、`low`は非秘密の内部情報や大きな労力に対する小さな影響、`informational`は確認できたごく小さい影響。確度と重大度を混ぜない。

## 必要な資料から読む

| 作業 | 必ず読む資料 |
|---|---|
| 完全監査の開始、プロファイル・予算・既存結果の扱い | [監査計画](AUDIT-PLANNING.md)。探索エージェントを起動する前の厳密な予算ゲートもここにある。 |
| 構造・境界・対象範囲を調べ、台帳を作る | [RECONNAISSANCE.md](RECONNAISSANCE.md) |
| 候補を探す、並行経路を追う、探索漏れを調べる | [HUNTING.md](HUNTING.md)、[ATTACK-CLASSES.md](ATTACK-CLASSES.md)と適用する分野別資料 |
| 候補を反証する、JSON化する、最終確認・報告を行う | [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md)。レコード作成直前に[report-schema.json](report-schema.json)も読む。 |
| 対象コードの実行、証跡保存、委任の書き込み先設定 | [EXECUTION-SAFETY.md](EXECUTION-SAFETY.md) |

分野別資料はATTACK-CLASSES.mdの選択条件と、ソースで確認した信頼境界から選ぶ。言語・依存名があるだけで全資料を読まない。複数分野をまたぐ経路には該当する条件を合わせて適用する。選択したブロック本文を省略せず渡す方法はHUNTING.mdに従う。

## 完全監査の6工程

1. **把握と計画**：絶対パスの対象・スキル・出力先、コミットと作業ツリーの変更、プロファイル、範囲、予算を確定する。監査計画と実行・証跡保全を読み、予算ゲートを通してから調査を委任する。構造・信頼境界・前回結果から`architecture.md`と決定的な`coverage-ledger.json`を作る。
2. **範囲に基づく探索**：台帳単位で担当を割り当てる。入力からパーサー、認証・認可、正規化、状態・派生コピー、sinkまで追い、兄弟・旧式・一括・再試行・取消・移行・例外経路を比較する。各波の後に独立した範囲点検を行う。担当外の境界は未探索として親へ返す。
3. **候補の独立検証**：同じ根本原因は安定したfingerprintにまとめ、発見者とは別の検証者が現在のソースと最小の再現から反証を試みる。前回の確定候補も再検証する。
4. **構造化と検査**：親が判定済みの3種類のレコードを`findings.json`へ書く。検証前の候補をいずれの判定にも入れない。両検証器を通し、形式・意味のエラーを直す。
5. **最終レコードの独立確認**：確定と要検証の両方を新しい検証者が確認する。`quick`だけは工程3の独立検証者が兼ねる。判定強化や根本原因・経路・入力・観測結果・影響・重大度の実質的な変更には、さらに別の独立検証者を付ける。独立性・予算が足りなければ争点のレコードを外し、未解決候補と未完了理由を残す。
6. **報告**：検証済みレコードと台帳から`REPORT.md`、`FINDINGS-DETAIL.md`、`NEEDS-VALIDATION.md`を作る。確定、要検証、改善メモ、除外・保留を区別する。修正案は最後の信頼できる判断点で不変条件を守る最小の変更と回帰例を示す。

親は共有ファイルの唯一の書き手。`research`は読み取り中心の調査・事実確認、`general`は広い調査・条件を満たす限定実行の担当を表す。実行基盤の相当する委任機能を使い、役割、独立性、プロンプト、書き込み分離を維持する。

台帳の作成・更新後と報告前に`node <skill-dir>/validate-coverage-ledger.cjs <output-dir>/coverage-ledger.json`を実行する。工程4と工程5でレコードを置換するたびに`node <skill-dir>/validate-findings.cjs <output-dir>/findings.json`と台帳検証器を実行する。通過が証明するのは構造・整合性であり、脆弱性の真偽ではない。

完全監査は、工程6の全成果物と両検証器の通過、または`run_status: "incomplete"`・正確な理由・報告書での不足開示のどちらかで終える。`complete`への更新は工程6と最終検査の後に行う。対象範囲を一度調べただけで網羅したと主張しない。
